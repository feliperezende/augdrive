# Project Knowledge Graph Builder

## Purpose

Transform a verified project context into a navigable model of system behavior.

This skill consumes:

```text
.ai/artifacts/project-context.yaml
```

and produces:

```text
.ai/artifacts/project-knowledge-graph.yaml
```

The goal is to answer:

* How does the system work?
* What depends on what?
* What sequence of events occurs?
* What breaks when something changes?
* Where are architectural bottlenecks?

This skill does not discover new facts.

It models relationships between existing facts.

---

# Input

Required:

```yaml
project_context:
```

generated by Context Builder.

Never use unsupported assumptions.

Any relationship not supported by facts must be marked as inferred.

---

# Core Rule

Every graph edge must have:

```yaml
source:
target:
relationship:
classification:
confidence:
```

Example:

```yaml
source: ScannerScreen

target: useScannerController

relationship: depends_on

classification: fact

confidence: 100
```

---

# Phase 1: Domain Mapping

Identify major domains.

Output:

```yaml
domains:

  scanning:

  recognition:

  persistence:

  configuration:

  navigation:
```

Domains represent bounded areas of responsibility.

---

# Phase 2: Relationship Extraction

Build relationships.

Output:

```yaml
relationships:

  - source: ScannerScreen
    target: useScannerController
    relationship: depends_on

  - source: useScannerController
    target: plateRecognizer
    relationship: calls

  - source: plateRecognizer
    target: NativeModule
    relationship: delegates_to
```

---

# Phase 3: Dependency Graph

Construct dependency graph.

Output:

```yaml
dependencies:

  ScannerScreen:
    depends_on:
      - useScannerController

  useScannerController:
    depends_on:
      - plateRecognizer

  plateRecognizer:
    depends_on:
      - NativeModule
```

---

# Phase 4: Entity Lifecycle Modeling

Track transformations.

Output:

```yaml
lifecycles:

  RecognitionResult:

    created_by:
      - OCR

    consumed_by:
      - CandidateTracker

  CandidatePlate:

    created_by:
      - CandidateTracker

    consumed_by:
      - TemporalConfirmation

  ConfirmedPlate:

    created_by:
      - TemporalConfirmation

    persisted_as:
      - PlateScan
```

---

# Phase 5: Flow Discovery

Model important workflows.

Output:

```yaml
flows:

  plate_recognition:

    - CameraFrame

    - OCR

    - PlateNormalization

    - ConfidenceValidation

    - CandidateTracking

    - TemporalConfirmation

    - ConfirmedPlate

    - LocationAcquisition

    - DatabasePersistence
```

A flow represents behavior.

Not implementation.

---

# Phase 6: State Machine Construction

Identify state transitions.

Output:

```yaml
state_machines:

  ScannerState:

    idle:
      transitions:
        - ready

    ready:
      transitions:
        - warming_up

    warming_up:
      transitions:
        - scanning
        - error

    scanning:
      transitions:
        - candidate_found
        - error

    candidate_found:
      transitions:
        - confirmed
        - scanning

    confirmed:
      transitions:
        - scanning

    error:
      transitions:
        - ready
```

---

Map ownership.

    owns:

    owns:
      - ScannerState

# Phase 8: Impact Analysis Graph

Determine change propagation.

Output:

```yaml
impacts:

  confirmationFrames:

    affects:
      - CandidateTracking
      - TemporalConfirmation
      - ConfirmedPlate
      - DatabasePersistence

  confidenceThreshold:

    affects:
      - CandidateTracking
      - ConfirmationRate
```

---

# Phase 9: Bottleneck Detection

Identify highly connected nodes.

Output:

```yaml
bottlenecks:

  - useScannerController

  - NativeModule

  - DatabaseService
```

These represent architectural hotspots.

---

# Phase 10: Risk Graph

Identify risky dependencies.

Output:

```yaml
risks:

  - source: NativeModule
    risk: platform_specific_behavior

  - source: DatabaseService
    risk: unbounded_growth
```

---

# Validation Rules

The graph must answer:

1. How does data move?
2. How does control move?
3. How do entities evolve?
4. What happens when X changes?
5. Which nodes are critical?

If these questions cannot be answered, the graph is incomplete.

---

# Prohibited Behavior

Do not:

* Invent flows
* Invent dependencies
* Invent state transitions
* Convert inferences into facts

Use:

```yaml
classification: inferred
confidence: 45
```

when certainty is insufficient.

The graph is a model, not a guess.
